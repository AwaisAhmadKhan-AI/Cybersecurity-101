# SSH (Secure Shell)

## What is SSH?

**SSH (Secure Shell)** is a secure network protocol used to remotely access and manage another computer over an encrypted connection.

It provides:
- Secure remote login
- Secure command execution
- Secure file transfer (SCP/SFTP)

Unlike Telnet, **SSH encrypts all communication**, preventing attackers from reading your data.

---

# SSH Authentication Process

SSH authentication has **two main parts**:

1. Authenticating the **Server**
2. Authenticating the **Client**

---

# 1. Authenticating the Server

When you connect to an SSH server for the **first time**, your SSH client doesn't know whether the server is genuine.

Example:

```bash
ssh 10.10.244.173
```

Output:

```text
The authenticity of host '10.10.244.173' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxx
Are you sure you want to continue connecting (yes/no)?
```

### Why does SSH ask this?

Because someone could be pretending to be the real server.

This is called a:

> **Man-in-the-Middle (MITM) Attack**

The SSH client asks whether you trust the server's **public key fingerprint**.

If you type:

```text
yes
```

SSH saves the server's public key inside:

```text
~/.ssh/known_hosts
```

Next time:

- If the key is the same → SSH connects silently.
- If the key changes → SSH warns you because someone may be impersonating the server.

---

# What is a Fingerprint?

A fingerprint is a **short unique hash** of the server's public key.

Example:

```text
SHA256:lLzhZc7YzRBDchm02qTX0qsLqeeiTCJg5ipOT0E/YM8
```

Instead of comparing the entire public key, you compare its fingerprint.

---

# 2. Authenticating the Client

Now the server needs to verify **who you are**.

There are two common methods:

- Username + Password
- SSH Key Authentication (recommended)

---

# SSH Key Authentication

Instead of passwords, SSH can use a **public/private key pair**.

The client proves its identity using the private key.

The server verifies it using the public key.

---

## How it works

```
Client
------
Private Key  --------------------> (Used to prove identity)

Public Key  ---------------------> Stored on server

Server
------
Checks whether the public key matches the client's private key.
```

Only someone with the **private key** can successfully authenticate.

---

# Generating SSH Keys

SSH keys are created using:

```bash
ssh-keygen
```

Example:

```bash
ssh-keygen -t ed25519
```

Output:

```text
Generating public/private ed25519 key pair.
```

SSH creates two files:

```
id_ed25519
```

Private Key

and

```
id_ed25519.pub
```

Public Key

---

# Public Key

Example:

```text
ssh-ed25519 AAAAC3Nza...
```

The public key:

- Can be shared
- Is copied to remote servers
- Is used for verification

---

# Private Key

Example:

```text
-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----
```

The private key:

- Must **never** be shared
- Stays on your computer
- Proves your identity

Think of it like your house key.

Anyone with it can access your systems.

---

# Supported SSH Key Algorithms

SSH supports several algorithms.

## 1. RSA

- Most common
- Larger key sizes
- Default for many systems

---

## 2. DSA

Digital Signature Algorithm

- Older
- Mostly obsolete

---

## 3. ECDSA

Elliptic Curve Digital Signature Algorithm

- Smaller keys
- Faster than RSA

---

## 4. ECDSA-SK

ECDSA using a hardware security key.

Example:

- YubiKey

Provides stronger protection.

---

## 5. Ed25519

Modern signature algorithm based on elliptic curves.

Advantages:

- Very secure
- Very fast
- Small keys
- Recommended for new SSH keys

---

## 6. Ed25519-SK

Ed25519 with hardware security keys.

Provides extra protection by storing the private key in hardware.

---

# Protecting the Private Key

Your private key should be treated exactly like a password.

Never:

- Upload it
- Email it
- Share it
- Commit it to GitHub

If someone gets your private key, they may log in to any server that trusts it.

---

# Passphrase

When creating a key, SSH asks:

```text
Enter passphrase:
```

The passphrase encrypts the private key.

Important:

The passphrase **does NOT authenticate you to the server**.

It only protects your private key on your own computer.

Even if someone steals your private key file, they still need the passphrase to use it.

---

# Where SSH Stores Keys

Default location:

```text
~/.ssh/
```

Example:

```
~/.ssh/
│
├── id_ed25519
├── id_ed25519.pub
├── known_hosts
└── authorized_keys
```

---

# known_hosts

Stores the fingerprints of servers you've trusted.

Example:

```text
Server A fingerprint

Server B fingerprint
```

This prevents man-in-the-middle attacks.

---

# authorized_keys

Located on the **server**.

Path:

```text
~/.ssh/authorized_keys
```

Contains the **public keys** of users allowed to log in.

Example:

```text
ssh-ed25519 AAAAC3Nza...
ssh-rsa AAAAB3...
```

If your public key is listed here, you can log in using the matching private key.

---

# Using a Specific Private Key

Sometimes your private key has a custom name.

Specify it using:

```bash
ssh -i privateKeyFileName user@host
```

Example:

```bash
ssh -i id_ed25519 root@192.168.1.10
```

---

# File Permissions

SSH ignores insecure private keys.

Correct permissions:

```bash
chmod 600 id_ed25519
```

Meaning:

- Owner can read/write
- Nobody else can access it

---

# Copying Public Key to Server

Instead of manually editing `authorized_keys`, use:

```bash
ssh-copy-id user@host
```

This copies your public key to the server.

Your private key **never leaves your computer**.

---

# SSH Keys During Pentesting / CTFs

SSH keys are often used to upgrade unstable shells.

Instead of relying on a reverse shell:

- Generate an SSH key
- Add the public key to:

```text
~/.ssh/authorized_keys
```

Now you can log in directly:

```bash
ssh user@target
```

Advantages:

- Stable shell
- Tab completion
- Command history
- Ctrl+C works correctly
- Easier file transfer

This technique is often called creating an **SSH backdoor** because access remains as long as the public key stays in `authorized_keys`.

---

# Key Points

- SSH provides encrypted remote access.
- The server proves its identity using its **public key fingerprint**.
- The client proves its identity using a **private key**.
- SSH key authentication is more secure than passwords.
- `ssh-keygen` generates public/private key pairs.
- The **public key** is shared; the **private key** must remain secret.
- `known_hosts` stores trusted server fingerprints.
- `authorized_keys` stores users' public keys allowed to log in.
- `ssh-copy-id` copies your public key to a server.
- Use `chmod 600` to secure private key permissions.
- During penetration testing, SSH keys can provide a stable shell and persistent access.
